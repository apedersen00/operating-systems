\section{Question 2 - Scheduler Criteria}

Provide concrete examples to illustrate scenarios when the following scheduling criteria conflict:

\begin{enumerate}[label=\alph*)]
    \item Average Turnaround Time vs Maximum Waiting Time
    \item Response Time vs Maximum Waiting Time
    \item System Job Throughput vs Response Time
\end{enumerate}

\solution

\subsection*{a) Average Turnaround Time and Maximum Waiting Time}

In this case, if we want to minimise average turnaround time and maximum waiting time, it can lead to conflicts. If process A is currently running, and the waiting time of some process in the ready queue has reached its maximum, process A will be interrupted and replaced by the new process. 
In one example, If we minimise the maximum waiting time to some minimum value k, and set the number of processes in the ready queue to be large, there will be a large number of new processes replacing previous processes. It will take a long time until a single process is fully completed, thus increasing the average turnaround time (this is a conflict).

In another example, if we want to minimise the average turnaround time, we cannot have too much context switching between processes. Processes will most likely run indefinitely until process finishes. If a particular process takes a very long time to run, the waiting time of the other processes will increase. The maximum waiting time must thus be increased to accommodate less context switching. Average turnaround time is reduced but maximum waiting time is increased.

\subsection*{b) Response Time and Maximum Waiting Time}

In this case, if we want to minimise response time and maximum waiting time, it can lead to conflicts. 
One example that will be given here is similar to the one above. Assume we set the number of processes in the ready queue to be large, and have their burst times be similar but much larger than their maximum waiting time. We assume the maximum waiting time in this case is minimised. Once the first process is run, it won’t take long until it is replaced by another process in the queue. This process of replacing continues to happen again and again. Given that the number of processes to run is large, it will take a long time until a single process is thoroughly completed for the first time, thus increasing response time.

Another example is if we wish to minimise response time. Imagine a scenario of time-consuming processes of similar length. To minimise response time, the processes should run without interruption until termination, as interruptions create overhead, delaying any process from being completed first. When a process runs without interruption, the waiting time of the remaining processes increases. If we try to minimise the maximum waiting time in this case, more interruptions will be caused, thus increasing response time. Minimising one side increases the other side. This is a conflict.


\subsection*{c) System Job Throughput and Response Time}

In this case, if we want to minimise response time and maximise throughput, it can lead to conflicts. This is mainly caused by the overhead created when we do context switching.

An example would be: Consider a system where there are “quick” processes and “slow” processes running, e.g. retrieving an HTML file and rendering a large file respectively. Imagine the slow process is running in the background. If we minimise response time, when the call for the quick process is received, to reduce response time and have a response returned as soon as possible, the slow process will be switched to the quick process and switched back once completed. This indeed reduces response time; however, due to the overhead created by context switching, the time taken to complete the slow processes increases, thus the system job throughput decreases.

\section{Question 3 - Thread creation, termination, and synchronization}

Write a C program to use a group of threads to parallelize the sum of an array.

\begin{enumerate}
    \item The master threads performs a Serial Sum first. It creates an array of 1,000,000 random floats in [0, 1], and prints out the sum of the array.
    \item Then, a group of worker threads are created. Each thread is assigned wiht a unique ID.
    \item Modify the code so that each thread sums up a portion of the array, and a final result is aggregated by the master thread from all threads' results and print out. Briefly describe your design of work distribution among threads.
    \item Add 2 timers. One measures the time spent in the serial sum and one measures the parallel sum.
    \item Run your program with 4, 8, 12, 16 threads.
    \item Make a bar chart to visualize your results.
\end{enumerate}

\solution

To parallelize the summing of the array, we first generate the array and compute the serial sum. The array is filled with random floats in range $[0, 1]$ using \lstinline{rand()}:

\begin{cppcode}{q3.c - Initialization and serial summing of array}
srand(time(NULL));
for (int i = 0; i < ARR_SIZE; i++)
{
    arr[i] = (float)rand() / (float)(RAND_MAX);
}

double sum_serial = 0.0;
for (int i = 0; i < ARR_SIZE; i++)
{
    sum_serial += arr[i];
}
\end{cppcode}

For parallelization, each thread computes a partial sum of a slice of the array. All sums are stored in doubles to improve precision. To pass information to the threads we defined a small struct:

\begin{cppcode}{q3.c - Struct for thread arguments}
typedef struct{
    int thread_id;
    double *partial_sums;
} thread_arg_t;
\end{cppcode}

\begin{itemize}
    \item \textbf{thread\_id}: Thread identifier. Used to compute it's corresponding chunk of the array.
    \item \textbf{partial\_sums}: Points to an array allocated in the main thread, where each thread will store it's result in a distinct slot.
\end{itemize}

Threads are created as follows:

\begin{cppcode}{q3.c - Creation of threads}
pthread_t *workers = malloc(sizeof(pthread_t) * num_threads);
double *partial_sums = malloc(sizeof(double) * num_threads);

for (int i = 0; i < num_threads; i++)
{
    thread_arg_t *arg = malloc(sizeof(thread_arg_t));
    arg->thread_id = i;
    arg->partial_sums = partial_sums;
    pthread_create(&workers[i], NULL, thread_func, arg); 
}
\end{cppcode}

Each thread executes a function, \lstinline{thread_func}, that computes its partial sum and stores it in the allocated array.

\begin{cppcode}{q3.c - Thread computation of array partial sum}
void *thread_func(void *arg) { 
    thread_arg_t *data = (thread_arg_t *)arg;
    int my_id = data->thread_id;
    double *partial_sums = data->partial_sums;
    free(arg);

    int chunk_size = ARR_SIZE / num_threads;
    int start = my_id * chunk_size;
    int end = (my_id == num_threads - 1) ? ARR_SIZE : start + chunk_size;

    double thread_sum = 0.0;
    for (int i = start; i < end; i++)
        thread_sum += arr[i];

    partial_sums[my_id] = thread_sum;

    printf("Thread %d sum = %f\n", my_id, thread_sum);
    pthread_exit(0);
}
\end{cppcode}

Once all threads have finished, the main thread sums the partial sums from the threads:

\begin{cppcode}{q3.c - Final sum from thread partial sums}
double sum_parallel = 0.0;
for (int i = 0; i < num_threads; i++)
{
    sum_parallel += partial_sums[i];
}
\end{cppcode}

By storing each threads partial sum in the array, we don't need to use mutex locks for access to a global variable. Example output from the application is shown below:

\begin{textcode}{> ./q3 8}
--- Master Sum ---
Serial sum:   500320.812500,    Serial time: 2224 us

--- Threads ---
Thread 0 sum = 62695.894531
Thread 1 sum = 62552.230469
Thread 2 sum = 62480.328125
Thread 3 sum = 62469.359375
Thread 4 sum = 62528.675781
Thread 5 sum = 62318.031250
Thread 6 sum = 62521.257812
Thread 7 sum = 62764.535156

--- Thread Sum ---
Parallel Sum: 500330.312500,    Parallel time: 1038 us
\end{textcode}

To measure the performance of the approach and how it scales with the number of threads, a Python script was created that run the application 100 times for $\text{num\_threads} \in [1, 16]$. The result is shown in \cref{fig:q3_exe}. We see that compared to the simple, serial approach this is some overhead in the creation of threads, as $\text{num\_threads} = 1$ is slightly slower than the baseline. However, as the number of threads is increased we see a performance increase until $\text{num\_threads} > 6$, whereafter the overhead of thread creation diminishes performance. On our system the optimal number of threads is therefore $\text{num\_threads} = 6$.

\section{Question 4 - Multi-threaded Histogram}

Write a C program to create a group of threads to parallelize building the histogram of an array. You should use 30 bins for the histogram. You can reuse code from Question 3.

\begin{enumerate}
    \item Modify the code so that it creates an array of doubles, the array length is given by \lstinline{argv[2]}. The array should be initialized with random values in the range $[0.0, 1.0]$.
    \item Serial histogram: add code to create the histogram of the array. Print out the histogram and time.
    \item Parallel histogram: Modify the thread function so that each thread builds the histogram of a portion of the array, and a final histogram is aggregated from all threads' result. Print out the histogram and time.
    \item Briefly describe your design of shared data structures and synchronization.
    \item Run your code: \lstinline{./program 3 10000}, \lstinline{./program 3 100000}, \lstinline{./program 3 1000000}. Include screenshots of your output here.
    \item Plots that visualize the output histogram. Analyze your results.
\end{enumerate}

\solution

To parallelize the histogram binning of the array, we first generate the array and compute the serial histogram:

\begin{cppcode}{q4.c - Initialization and serial histogram computation}
arr = malloc(sizeof(double) * arr_size);
srand(time(NULL));
for (int i = 0; i < arr_size; i++)
{
    arr[i] = (double)rand() / (double)(RAND_MAX);
}

int hist_serial[NUM_BINS] = {0};
for (int i = 0; i < arr_size; i++)
{
    int bin = (int)(arr[i] * NUM_BINS);
    if (bin == NUM_BINS) bin = NUM_BINS - 1;
    hist_serial[bin]++;
}
\end{cppcode}

For parallelization, the array is split into chunks with each thread computing a partial histogram for its assignment part. To pass thread specific information, a struct is again used:

\begin{cppcode}{q4.c - Struct for thread arguments}
typedef struct{
    int thread_id;
    int (*partial_histogram)[NUM_BINS];
} thread_arg_t;
\end{cppcode}

\begin{itemize}
    \item \textbf{thread\_id}: Thread identifier. Used to compute it's corresponding chunk of the array.
    \item \textbf{partial\_histograms}: Pointer to an array of partial histograms (one per thread).
\end{itemize}

\vspace{-10pt}
Threads are created as follows:

\begin{cppcode}{q4.c - Creation of threads}
pthread_t *workers = malloc(sizeof(pthread_t) * num_threads);
int (*partial_histograms)[NUM_BINS] = calloc(num_threads, sizeof(*partial_histograms));

for (int i = 0; i < num_threads; i++)
{
    thread_arg_t *arg = malloc(sizeof(thread_arg_t));
    arg->thread_id = i;
    arg->partial_histogram = partial_histograms;
    pthread_create(&workers[i], NULL, thread_func, arg);
}
\end{cppcode}

Each thread executes a function, \lstinline{thread_func}, that computes its partial histogram and stores it in the allocated array:

\begin{cppcode}{q4.c - Thread computation of array partial histogram}
void *thread_func(void *arg)
{
    thread_arg_t *data = (thread_arg_t *)arg;
    int tid = data->thread_id;
    int (*partial_histograms)[NUM_BINS] = data->partial_histogram;
    free(arg);

    int chunk_size = arr_size / num_threads;
    int start = tid * chunk_size;
    int end = (tid == num_threads - 1) ? arr_size : start + chunk_size;

    for (int i = start; i < end; i++) {
        int bin = (int)(arr[i] * NUM_BINS);
        if (bin == NUM_BINS) bin = NUM_BINS - 1;
        partial_histograms[tid][bin]++;
    }
    pthread_exit(NULL);
}
\end{cppcode}

Once all threads have finished, the main thread adds the partial histograms to form the total histogram:

\begin{cppcode}{q4.c - Final histogram from partial histograms}
int hist_parallel[NUM_BINS] = {0};
for (int t = 0; t < num_threads; t++)
{
    for (int b = 0; b < NUM_BINS; b++)
    {
        hist_parallel[b] += partial_histograms[t][b];
    }
}
\end{cppcode}

Just like before, by storing each threads partial histogram in a dedicated array, we don't need mutex locks for access to e.g. a global array. Example output from the application is shown below:

\section{Question 5 - Lock-free Synchronization}

Compare and swap (CAS) instructions leverages hardware atomics on today's computers and can be used to design lock-free data structures. Write a C program to implement Stack as a linked list of Nodes and each thread can perform \lstinline{push()} and \lstinline{pop()} on it.

\begin{itemize}
    \item Each thread performs two functions, \lstinline{push()} for adding a node to the linked list of nodes, and \lstinline{pop()} for removing the top node from the linked list. The code should print out the number of nodes remaining in Stack.
    \item In \lstinline{pop()} and \lstinline{push()}, add the implementation based on mutex lock to update top.
    \item Briefly describe the global data structures in your code and how are access synchronized on them.
    \item Run your program with 1, 2, 4, 8, 16, 32 threads.
    \item In \lstinline{pop()} and \lstinline|push()|, add the implementation based on compare-and-swap (CAS) operations to update top.
    \item Briefly describe the global data structures in your code and how are access synchronized on them.
    \item Run your program with 1, 2, 4, 8, 16, 32 threads.
\end{itemize}

\solution

We define a simple node struct for the linked-list, along with a global pointer, \texttt{top} which always points to the head of the stack. A global counter, \texttt{global\_node\_id} is used to generate unique IDs for each node pushed by the threads.

\begin{cppcode}{q5.c - Node structure and global variables}
typedef struct node {
    int node_id;        // Unique ID for node
    struct node *next;  // Pointer to next node in stack
} Node;

Node *top = NULL;       // Top of the stack
int global_node_id = 0; // Global counter for node IDs
\end{cppcode}

\subsection*{Mutex Approach}

In this approach, access to update top of the shared stack is synchronized using a mutex lock. The \texttt{push\_mutex()} function creates a new node, locks the mutex, and then inserts the node at the top of the stack. Afterwards the lock is released. Similarly we have \texttt{pop\_mutex()} which removes and frees the top node while ensuring synchronized access by use of a mutex lock.

\begin{cppcode}{q5.c - Stack operations using mutex lock}
void push_mutex() {
    Node *new_node;
    new_node = malloc(sizeof(Node));

    pthread_mutex_lock(&stack_mutex);
    new_node->node_id = global_node_id++;
    new_node->next = top;
    top = new_node;
    pthread_mutex_unlock(&stack_mutex);
}

int pop_mutex() {
    Node *old_node;
    int node_id = -1;

    pthread_mutex_lock(&stack_mutex);
    if (top != NULL) {
        old_node = top;
        node_id = old_node->node_id;
        top = top->next;
        free(old_node);
    }
    pthread_mutex_unlock(&stack_mutex);
    return node_id;
}
\end{cppcode}

\subsection*{CAS Approach}

In this approach we use atomic \textit{Compare-and-Swap} operations. There are two ways we could have approached this in code, either we utilize the \texttt{stdatomic.h} library and define atomic variables and utilize their methods, or we directy use the GCC \texttt{\_\_sync} intrinsics directly. We chose the latter due to it being slightly clearer what's going on in this particular case. The two intrinsic functions we utilize are \cite{gcc_sync_builtins}:

\begin{itemize}
    \item \texttt{\_\_sync\_fetch\_and\_add(type *ptr, type value)}: Atomically fetches and adds a value to a variable.
    \item \texttt{\_\_sync\_bool\_compare\_and\_swap(type *ptr, type oldval, type newval)}: Perform an atomic compare and swap. If the current value of \texttt{*ptr} is \texttt{oldval}, then write \texttt{newval} into \texttt{*ptr}. The bool versions returns true if the comparison is successful.
\end{itemize}

Utilizing the above CAS functions, the top pointer can updated by the threads without the need of acquiring a lock first. This allows multiple threads to operate concurrently without interfering with each other. In other words, the CAS functions ensures atomicity of the update of top. If another thread updates \texttt{top} between reading and writing, the CAS fails and the operation is simply retried.

\begin{cppcode}{q5.c - Stack operations using compare-and-swap (CAS)}
void push_cas() {
    Node *new_node;
    Node *old_top;
    new_node = malloc(sizeof(Node));

    do {
        old_top = top;
        new_node->node_id = __sync_fetch_and_add(&global_node_id, 1);
        new_node->next = old_top;
    } while (!__sync_bool_compare_and_swap(&top, old_top, new_node));
}

int pop_cas() {
    Node *old_top;
    Node *new_top;
    int node_id = -1;

    do {
        old_top = top;
        if (old_top == NULL)
        {
            return -1;
        }
        new_top = old_top->next;
        node_id = old_top->node_id;
    } while (!__sync_bool_compare_and_swap(&top, old_top, new_top));

    free(old_top);
    return node_id;
}
\end{cppcode}

\subsection*{Thread Creation}

void print_remaining_nodes() {

}

\section{Question 6 - Resource-Allocation Graph}

Recall that a resource-allocation graph without cycles has no deadlock, and a resource-allocation graph with cycles may or may not have deadlocks. In the following resource-allocation graphs:

\begin{center}
    \includegraphics[width=0.8\textwidth]{assets/q6.png}
\end{center}

\begin{enumerate}[label=\alph*)]
    \item Please describe thread states in each graph. For example, thread T0 is requesting an instance of resource R0, thread T1 is holding an instance of resource R1.

    \item Which graph(s) have no deadlocks? Please illustrate the order in which the threads may complete execution. For example, thread T0 releases an instance of resource R0, and then an instance of resource R0 is allocated to thread T1.

    \item Which graph may have deadlocks? Recall that a cycle in the resource-allocation graph does not necessarily mean deadlock. For those situations that are deadlocked, provide the cycle of threads and resources. For example, \{T0->R0->T1->R1->T0\}.
\end{enumerate}

\solution

\subsection*{a)}

In Figure A, T1 has been allocated 1 instance of R1 and requests 1 instance of R2, T2 has been allocated 1 instance of R2, and T3 requests 1 instance of R2.  
In Figure B, T1 requests R1 and has been allocated 1 instance of R2, T2 requests 1 instance of R3 and has been allocated 1 instance of R2 and R1, and T3 has been allocated 1 instance of R3.  
In Figure C, T1 requests 1 instance of R2 and has been allocated 1 instance of R1, T2 requests 1 instance of R2 and has been allocated 1 instance of R3, T3 requests 1 instance of R1 and has been allocated 1 instance of R2, T4 has been allocated with both 1 instance of R2 and 1 instance of R3.

\subsection*{b)}

Figures A and B do not have deadlocks, as they do not contain any cycles. Figure C, although having cycles, does not have deadlocks.  

For Figure A, the order can be: T2 releases 1 instance of R2; 1 instance of R2 is allocated to T3; T3 releases 1 instance of R2; 1 instance of R2 is allocated to T1; T1 releases 1 instance of R2 and R1.  

For Figure B, the order can be: T3 releases 1 instance of R3; 1 instance of R3 is allocated to T2; T2 releases 1 instance of R1 and R2; 1 instance of R1 is allocated to T1; T1 releases 1 instance of R1 and R2.  

For Figure C, the order can be: T4 releases 1 instance of R2 and R3; 1 instance of R2 is allocated to T2; T2 releases 1 instance of R2 and R3; 1 instance of R2 is allocated to T1; T1 releases 1 instance of R1 and R2; 1 instance of R2 is allocated to T3; T3 releases 1 instance of R1 and R2.

\subsection*{c)}

Figure C may have deadlocks, as it is the only one with cycles in its graph. However, T4 should eventually release R3 and R2, causing R1 accessible to T1. Once T1 is completed and releases R1 and R2, no cycle can be found again. Thus, there is no actual deadlock in this figure.

\section{Question 7 - Banker's Algorithm}

Given the following system snapshot:

\begin{table}[h!]
    \centering
    \begin{tabular}{|c|cccc|cccc|cccc|}
        \hline
        \textbf{Processes} & \multicolumn{4}{c|}{\textbf{Allocation}} & \multicolumn{4}{c|}{\textbf{Max}} & \multicolumn{4}{c|}{\textbf{Available}} \\
        \hline
        & A & B & C & D & A & B & C & D & A & B & C & D \\
        \hline
        P0 & 0 & 0 & 1 & 2 & 0 & 0 & 1 & 2 & 1 & 5 & 2 & 0 \\
        P1 & 1 & 0 & 0 & 0 & 1 & 7 & 5 & 0 &  &  &  &  \\
        P2 & 0 & 3 & 5 & 4 & 2 & 3 & 5 & 6 &  &  &  &  \\
        P3 & 0 & 6 & 3 & 2 & 0 & 6 & 5 & 2 &  &  &  &  \\
        P4 & 0 & 0 & 1 & 4 & 0 & 6 & 5 & 6 &  &  &  &  \\
        \hline
    \end{tabular}
    \caption{System Snapshot}
\end{table}

\begin{enumerate}[label=\alph*)]
    \item List the number of instances per resource. List down the need matrix.
    \item Assume process P1 requests for (0, 4, 2, 0), can the request be granted immediately? Explain your answer.
    \item Run the Banker's safety check algorithm. Answer whether the system is in a safe state. Explain your answer.
    \item Identify a safe sequence of processes.
\end{enumerate}

\solution

\subsection*{a)}

The total number of instances per resource is calculated as the sum of allocated resources plus the currently available resources:

\vspace{-10pt}
\[
\begin{aligned}
R0 &= (0 + 1 + 0 + 0 + 0) + 1 = 2 \\

R2 &= (1 + 0 + 5 + 3 + 1) + 2 = 12 \\
R3 &= (2 + 0 + 4 + 2 + 4) + 0 = 12
\end{aligned}
\]

Therefore, the total number of instances for each resource type is:
\[
R0 = 2, \quad R1 = 14, \quad R2 = 12, \quad R3 = 12
\]

\vspace{-10pt}
The Need Matrix represents the remaining resources each process still needs to complete its execution. It is calculated as Need = Max - Allocation:

\begin{table}[h]
    \centering
    \begin{tabular}{|c|cccc|}
        \hline
        \textbf{Process} & R0 & R1 & R2 & R3 \\
        \hline

        P1 & $1-1=0$ & $7-0=7$ & $5-0=5$ & $0-0=0$ \\
        P2 & $2-1=1$ & $3-3=0$ & $5-5=0$ & $6-4=2$ \\
        P3 & $0-0=0$ & $6-6=0$ & $5-3=2$ & $2-2=0$ \\
        P4 & $0-0=0$ & $6-0=6$ & $5-1=4$ & $6-4=2$ \\

\subsection*{b)}

Let 
\[
\text{Request}_{P1} = (0, 4, 2, 0)
\]

\textbf{Step 1: Check if Request $\le$ Need}  

The request must not exceed P1's maximum declared need:

\[
\text{Need}_{P1} = (0, 7, 5, 0), \quad 
\text{Request}_{P1} = (0, 4, 2, 0)
\]

\[
0 \le 0, \quad 4 \le 7, \quad 2 \le 5, \quad 0 \le 0
\]

All conditions are satisfied. Therefore,
\[
\text{Request}_{P1} \le \text{Need}_{P1}
\]

\medskip

\textbf{Step 2: Check if Request $\le$ Available}  

The request must not exceed the currently available resources:

\[
\text{Available} = (1, 5, 2, 0), \quad 
\text{Request}_{P1} = (0, 4, 2, 0)
\]

\[
0 \le 1, \quad 4 \le 5, \quad 2 \le 2, \quad 0 \le 0
\]

All conditions are satisfied. Therefore,
\[
\text{Request}_{P1} \le \text{Available}
\]

\medskip

Since both conditions are met, the request for P1 can be granted immediately in terms of current availability and P1's declared maximum need. However, to ensure the system remains in a safe state after granting the request, we must perform a safety check.

\subsection*{c)}

Let's assume P1's request for $(0, 4, 2, 0)$ is granted. The system state would change as follows:

\textbf{New Allocation for P1:}
\[
\begin{aligned}
\text{Old Allocation}_{P1} &= (1, 0, 0, 0) \\
\text{Request}_{P1} &= (0, 4, 2, 0) \\
\text{New Allocation}_{P1} &= (1+0, 0+4, 0+2, 0+0) = (1, 4, 2, 0)
\end{aligned}
\]

\textbf{New Available Resources:}
\[
\begin{aligned}
\text{Old Available} &= (1, 5, 2, 0) \\
\text{Request}_{P1} &= (0, 4, 2, 0) \\
\text{New Available} &= (1-0, 5-4, 2-2, 0-0) = (1, 1, 0, 0)
\end{aligned}
\]

\textbf{New Need for P1:}
\[
\begin{aligned}
\text{Old Need}_{P1} &= (0, 7, 5, 0) \\
\text{Request}_{P1} &= (0, 4, 2, 0) \\
\text{New Need}_{P1} &= (0-0, 7-4, 5-2, 0-0) = (0, 3, 3, 0)
\end{aligned}
\]

\medskip

Now, we run the Banker's Safety Algorithm with the new system state:

\textbf{Updated Allocation Matrix:}

\textbf{Updated Available Vector:}

\textbf{Safety Algorithm Steps:}

\begin{enumerate}
    \item Initialize $\text{Work} = \text{Available}_{new} = (1, 1, 0, 0)$
    \item Initialize $\text{Finish} = [\text{False}, \text{False}, \text{False}, \text{False}, \text{False}]$ for P0 to P4.
\end{enumerate}

\textbf{Iteration 1}

\begin{itemize}
    \item P0: Need = (0, 0, 0, 0). Is Need$_{P0} \le$ Work? $(0\le1, 0\le1, 0\le0, 0\le0)$ → True.
        \begin{itemize}
            \item Work = Work + Allocation$_{P0}$ = $(1,1,0,0) + (0,0,1,2) = (1,1,1,2)$  
            \item Finish[P0] = True
        \end{itemize}
\end{itemize}

\textbf{Iteration 2 (Processes P1, P2, P3, P4 are still False)}

\begin{itemize}
    \item P1: Need = (0, 3, 3, 0). Is Need$_{P1} \le$ Work? $(0\le1, 3\le1, 3\le1, 0\le2)$ → False (3>1)
    \item P2: Need = (1, 0, 0, 2). Is Need$_{P2} \le$ Work? $(1\le1, 0\le1, 0\le1, 2\le2)$ → True.
        \begin{itemize}
            \item Work = Work + Allocation$_{P2}$ = $(1,1,1,2) + (1,3,5,4) = (2,4,6,6)$  
            \item Finish[P2] = True
        \end{itemize}
\end{itemize}

\textbf{Iteration 3 (Processes P1, P3, P4 are still False)}

\begin{itemize}
    \item P1: Need = (0, 3, 3, 0). Is Need$_{P1} \le$ Work? $(0\le2, 3\le4, 3\le6, 0\le6)$ → True.
        \begin{itemize}
            \item Work = Work + Allocation$_{P1}$ = $(2,4,6,6) + (1,4,2,0) = (3,8,8,6)$  
            \item Finish[P1] = True
        \end{itemize}

            \item Work = Work + Allocation$_{P3}$ = $(3,8,8,6) + (0,6,3,2) = (3,14,11,8)$  
            \item Finish[P3] = True
        \end{itemize}

        \begin{itemize}
            \item Work = Work + Allocation$_{P4}$ = $(3,14,11,8) + (0,0,1,4) = (3,14,12,12)$  
            \item Finish[P4] = True
        \end{itemize}
\end{itemize}

All processes have Finish[i] = True.  

\textbf{Conclusion:} Yes, the system is in a safe state after P1's request for $(0,4,2,0)$ is granted, because a safe sequence exists.

\subsection*{d)}

Based on the safety check above, a safe sequence is:

\[
<P0, P2, P1, P3, P4>
\]

This sequence demonstrates that all processes can complete their execution without causing a deadlock, even after P1's request is granted.

\section{Question 8 - Minimum Resources}

Given the following system snapshot:

\begin{table}[h!]
    \centering
    \begin{tabular}{|c|cccc|cccc|cccc|}
        \hline
        \textbf{Processes} & \multicolumn{4}{c|}{\textbf{Allocation}} & \multicolumn{4}{c|}{\textbf{Max}} & \multicolumn{4}{c|}{\textbf{Available}} \\
        \hline
        & A & B & C & D & A & B & C & D & A & B & C & D \\
        \hline
        P0 & 1 & 0 & 1 & 2 & 1 & 0 & 1 & 2 & 0 & x & 4 & 1 \\
        P1 & 1 & 0 & 3 & 0 & 1 & 7 & 5 & 0 &  &  &  &  \\
        P2 & 1 & 3 & 5 & 4 & 2 & 3 & 5 & 6 &  &  &  &  \\
        P3 & 0 & 2 & 3 & 2 & 0 & 6 & 5 & 2 &  &  &  &  \\
        \hline
    \end{tabular}
    \caption{System Snapshot}
\end{table}

Determine the smallest value of x for which this is a safe state. Briefly explain how you derive the answer.

\solution

\textbf{Step 1: Compute the Need Matrix}  

The Need matrix is calculated as $\text{Need} = \text{Max} - \text{Allocation}$.

\[
\begin{aligned}
\text{P0 Need} &= [1, 0, 1, 2] - [1, 0, 1, 2] = [0, 0, 0, 0] \\
\text{P1 Need} &= [1, 7, 5, 0] - [1, 0, 3, 0] = [0, 7, 2, 0] \\
\text{P2 Need} &= [2, 3, 5, 6] - [1, 3, 5, 4] = [1, 0, 0, 2] \\
\text{P3 Need} &= [0, 6, 5, 2] - [0, 2, 3, 2] = [0, 4, 2, 0]
\end{aligned}
\]

\begin{table}[h!]
\centering
\begin{tabular}{|c|c|}
\hline
\textbf{Process} & \textbf{Need} \\
\hline
P0 & [0, 0, 0, 0] \\
P1 & [0, 7, 2, 0] \\
P2 & [1, 0, 0, 2] \\
P3 & [0, 4, 2, 0] \\
\hline
\end{tabular}
\caption{Need Matrix}
\end{table}

\medskip

\textbf{Step 2: Determine a Safe Sequence Using the Banker's Algorithm}  

For a state to be safe, there must exist a sequence of processes such that each process's Need is less than or equal to the Available resources. When a process executes, its Allocation is added back to Available.  

Let the initial Available vector be $[0, x, 4, 1]$. We try to find a safe sequence:

\medskip
\textbf{Trial 1: P0}  

\[
\text{Need}_{P0} = [0,0,0,0], \quad \text{Available} = [0, x, 4, 1]
\]

Since $\text{Need}_{P0} \le \text{Available}$ for any $x \ge 0$, P0 can execute.  

\[
\text{Available} = \text{Available} + \text{Allocation}_{P0} = [0,x,4,1] + [1,0,1,2] = [1,x,5,3]
\]

\medskip
\textbf{Trial 2: P3}  

\[
\text{Need}_{P3} = [0,4,2,0], \quad \text{Available} = [1,x,5,3]
\]

For P3 to execute, $[0,4,2,0] \le [1,x,5,3]$, which requires $x \ge 4$. If P3 executes:

\[
\text{Available} = [1,x,5,3] + [0,2,3,2] = [1,x+2,8,5]
\]

\medskip
\textbf{Trial 3: P2}  

\[
\text{Need}_{P2} = [1,0,0,2], \quad \text{Available} = [1,x+2,8,5]
\]

Since $[1,0,0,2] \le [1,x+2,8,5]$, P2 can execute.  

\[
\text{Available} = [1,x+2,8,5] + [1,3,5,4] = [2,x+5,13,9]
\]

\medskip
\textbf{Trial 4: P1}  

\[
\text{Need}_{P1} = [0,7,2,0], \quad \text{Available} = [2,x+5,13,9]
\]

To execute, $[0,7,2,0] \le [2,x+5,13,9]$ requires $7 \le x+5 \Rightarrow x \ge 2$.  

\medskip
\textbf{Combining Conditions:}  

From P3: $x \ge 4$ \\
From P1: $x \ge 2$  

\noindent Therefore, the smallest value of $x$ that satisfies all conditions is $x = 4$.  

\medskip
\textbf{Safe Sequence:}  

A possible safe sequence for $x=4$ is:

\[
\langle P0, P3, P2, P1 \rangle
\]
